# Entrega na EC2 existente

O workflow de CI roda em branches e PRs. Somente um push na `main` que passou pelas verificações habilita os jobs de imagens e produção. O runner constrói linux/amd64, publica três imagens GHCR com tag igual ao SHA, passa os digests imutáveis ao SSM e aguarda o resultado do comando. Depois consulta as URLs HTTPS públicas. Caddy, PostgreSQL e volumes ficam no projeto Compose existente. A EC2 não compila imagens. [Workflow](../../.github/workflows/ci.yml)

## Configuração inicial pelo administrador AWS e pelo mantenedor do GitHub

1. Na região da instância, confira que o SSM Agent está online em **Systems Manager → Fleet Manager**. Use um instance profile com as permissões de managed node (por exemplo `AmazonSSMManagedInstanceCore`). Garanta saída HTTPS para SSM, canais de mensagens, GHCR e seus endpoints de download. O runner dispensa acesso à porta 22. Confirme a arquitetura x86_64, Docker Compose v2 com `--wait`, Bash, Python 3, espaço de disco e volume Docker nomeado do PostgreSQL 16.
2. Em IAM, cadastre o provedor OIDC `https://token.actions.githubusercontent.com`, audiência `sts.amazonaws.com`. Crie uma role exclusiva para a entrega. Na confiança, limite `Principal.Federated` ao ARN desse provedor na conta, ação `sts:AssumeRoleWithWebIdentity`, e condições **StringEquals** sobre `token.actions.githubusercontent.com:aud` e `token.actions.githubusercontent.com:sub`. O subject clássico deste workflow é `repo:PabloSchuller/webapp-vedacao-industrial:ref:refs/heads/main`. Se o repositório usar subject imutável, ajuste ao formato com IDs reais da organização e do repositório, preservando a restrição à main. Proteja a main e revise alterações em workflows e imagens. [OIDC no GitHub](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws)
3. Crie o documento SSM **Command** chamado `VedacaoHubRelease`, versão 1, com o conteúdo de [documento-ssm.json](../../ops/documento-ssm.json). Na role do GitHub, conceda apenas `ssm:SendCommand` com os dois recursos `arn:aws:ssm:REGIAO:CONTA:document/VedacaoHubRelease` e `arn:aws:ec2:REGIAO:CONTA:instance/ID`, e `ssm:GetCommandInvocation` com recurso `*` (consulta de status). Substitua os marcadores antes de aplicar. A role não precisa de permissão para alterar o documento ou abrir sessões. [AWS Run Command](https://docs.aws.amazon.com/systems-manager/latest/userguide/run-command-setting-up.html)
4. No GitHub, habilite Actions e publicação em Packages. Configure **Settings → Secrets and variables → Actions → Variables**: `AWS_ROLE_ARN`, `AWS_REGION`, `INSTANCE_ID`. Os padrões de `PUBLIC_WEB_URL`, `PUBLIC_HEALTH_URL` e `PUBLIC_API_URL` apontam ao domínio público informado (API sob `/api`). Se o domínio mudar, atualize as três variáveis e o Caddy. Dê ao repositório acesso de escrita aos seus três pacotes. Para permitir pull anônimo das imagens, torne públicos somente os pacotes de código `webapp-vedacao-industrial/api`, `/web` e `/ia` no GHCR. Pacotes novos podem iniciar privados: após ajustar a visibilidade, reexecute o job de produção que falhou no pull. Credenciais da aplicação continuam no host.
5. Pela administração inicial do host via Systems Manager, instale a cópia **revisada** de [aplicar.sh](../../ops/aplicar.sh) como `/usr/local/sbin/vedacaohub-release`, root:root, modo 0755. Crie `/etc/vedacaohub` com modo 0700. O helper roda como root: restrinja alteração do script, do diretório da aplicação, dos arquivos Compose e das configurações a administradores confiáveis. Isso é configuração inicial do mecanismo, não uma atualização manual de aplicação.
6. Identifique o projeto pelo contêiner PostgreSQL ativo: `docker inspect -f '{{index .Config.Labels "com.docker.compose.project"}} {{index .Config.Labels "com.docker.compose.project.working_dir"}} {{index .Config.Labels "com.docker.compose.project.config_files"}}' ID_DO_CONTAINER`. Confira o nome do volume com `docker inspect -f '{{range .Mounts}}{{println .Name .Destination}}{{end}}' ID_DO_CONTAINER`. Crie `/etc/vedacaohub/release.conf` root:root, 0600, com os valores **efetivos da implantação**, por exemplo:

```bash
APP_DIR='/caminho/do/checkout-existente'
COMPOSE_PROJECT_NAME='projeto-existente'
COMPOSE_FILE='/caminho/compose-base.yml:/caminho/override-producao.yml'
PG_VOLUME='nome-real-do-volume-montado-em-/var/lib/postgresql/data'
BACKUP_DIR='/caminho/privado/em-volume-com-espaco'
```

Inclua em `COMPOSE_FILE` somente os arquivos base efetivamente usados, na mesma ordem, separados por dois-pontos. Se a instalação usa arquivo de ambiente fora do padrão, defina `COMPOSE_ENV_FILES` com seu caminho existente. O helper acrescenta o override persistente `/etc/vedacaohub/images.yml` automaticamente. Para inspeções posteriores use a mesma composição incluindo esse override. Preserve o `.env`. Verifique em particular que `api`, `web` e `ia` executam os artefatos da imagem, sem bind mounts sobre o código, que Caddy roteia o prefixo público para a API e que rede e volumes correspondem ao ambiente em uso. O helper foi preparado para o serviço `postgres` do projeto. Configurações diferentes exigem conferir o alvo antes da habilitação.

## Migrações, falhas e comprovação

O script verifica o histórico Prisma e os checksums das migrações aplicadas. Para uma **migração pendente**, revise o SQL, compatibilidade com a versão em execução, duração de locks e espaço de backup. Somente migrações aditivas compatíveis são admitidas neste processo. Após a revisão de cada arquivo, acrescente sua linha de `sha256sum prisma/migrations/NOME/migration.sql` (executado dentro de `api/` na revisão correspondente) ao arquivo root-only `/etc/vedacaohub/migracoes-aprovadas.sha256`. Evite aprovar um diretório inteiro. Um banco sem histórico conhecido ou com migração incompleta bloqueia o processo.

Com migrações pendentes, o helper executa `pg_dump -Fc` do banco configurado, confere o índice com `pg_restore --list` e somente então executa `prisma migrate deploy`. Mantenha o destino de backup privado, criptografado e com capacidade e retenção verificadas. A listagem do índice não comprova restauração; teste recuperação em banco descartável separado. Esta revisão não adiciona migrações.

Em uma falha, consulte o SHA e o ID do comando no job, depois **Systems Manager → Run Command → Command history**. Se o estado do banco for desconhecido, confira o histórico de migrações antes de repetir. Em falha transitória, reexecute o job na mesma ponta da main. Para reverter código, use um revert revisado pela main preservando a árvore das migrações já aplicadas. A recuperação do banco exige procedimento separado e autorização. Nenhum caminho do deploy chama seed, bootstrap de contas, down de volumes, reset ou db push.

A evidência de CD é uma execução da main com `verificar`, `imagens` e `producao` verdes, digests e Command ID correspondentes e sonda externa aprovada. A evidência de monitoramento recorrente fica em **Actions → Disponibilidade pública**, com hora UTC, duração e falhas por execução; o cron roda duas vezes por hora e pode sofrer atraso no GitHub. Habilite notificações de falhas de Actions para o responsável. A sonda não exige agente residente na t3.small. A saúde da IA é conferida internamente durante o deploy.
